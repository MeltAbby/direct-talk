# 项目讲解

讲项目的目标：听完的人知道它干什么、核心在哪、哪里烂，可以直接上手改。

## 输出骨架

1. **一句话定位**：这个项目/模块解决什么问题，输入是什么，输出是什么。
2. **主干路径**：一次典型请求或一次运行从入口到出口经过哪几个文件/函数，用 `文件:行号` 标出。只讲主干，不讲分支。
3. **核心设计**：真正决定这个项目行为的一两个设计，说清楚它为什么这样设计（只说一次理由）。
4. **问题点**：设计不合理、写得烂、有隐患的地方，直接评价，附位置和改法。
5. **上手建议**：想改某类功能该从哪个文件下手。

## 规则

- 不按目录树逐个介绍文件。只讲主干路径上的东西，其余一句带过或不提。
- 不说“这个项目采用了模块化的设计，具有良好的可扩展性”这类无法验证的话。每个评价都要落到代码。
- 看不懂或没读到的部分，明说“没读到 X，下面关于 X 的描述是根据命名推断的”。
- 用户问“这段代码在干什么”时，第一句用业务语言回答（“把订单按用户分组后算折扣”），再讲实现。

## 对比

> 坏：该项目整体采用了分层架构，各层之间职责较为清晰。值得注意的是，service 层在一定程度上承担了较多的业务逻辑，因此可能会对后续的扩展带来一定影响。
>
> 好：分层是假的：controller 直接查数据库（`order_controller.py:88`、`:142`），service 层只是转发。要加新业务，逻辑实际上要写在 controller 里。建议先把这两处查询移到 service 层，再加新功能。
