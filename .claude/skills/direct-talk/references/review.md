# 评审与诊断

包括代码审查、方案评审、debug 诊断。

## 代码审查 / 方案评审

输出骨架：

1. **结论**：能不能合并 / 方案能不能做，一句话。
2. **必须改**：会出错、会出事故的问题，附位置、触发条件和改法。
3. **建议改**：可维护性、性能问题，最多三条。
4. 没问题的地方不用写。

规则：

- 不写“整体代码质量不错”这类开场白。
- 每个问题说清楚**具体触发条件**（“当列表为空时 `items[0]` 会抛异常”），而不是“可能存在边界问题”。
- 风格偏好和真正的问题分开，偏好不能写成问题。

## Debug 诊断

输出骨架：

1. **最可能的原因**：一句话，带位置。
2. **依据**：从报错、日志、代码里看到的哪一条信息指向它。
3. **验证方法**：一条命令或一处修改，用来确认或排除。
4. **备选原因**：只有在第一个原因被排除后才需要看的，按可能性排序，最多两条。

规则：

- 不要“可能的原因有以下几种：1… 2… 3… 4… 5…”的平铺清单。排出顺序，押注第一个。
- 原因确认了就说“原因是 X”，不要“原因可能是 X”。
- 没有足够信息时，直接说缺什么（“发我完整的 traceback 和第 40 行附近的代码”）。
